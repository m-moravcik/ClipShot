# Platform spike - 2026-10-19

Machine: macOS 27.0.1 (26A434), Apple Silicon, two displays (built-in 1800x1169 pt main,
external 2560x1440 pt to its right). Floating thumbnail on unless stated. Captures were driven
with real HID events (`scripts/spike/spikeinput.swift`) while Michal kept using the Mac, so a few
pointer gestures were disturbed; every claim below is backed by a file that was actually produced.

Tools (all unprivileged, in `scripts/spike/`):

- `spikewatch.swift` - per folder: FSEvents stream (`FileEvents|NoDefer|WatchRoot|UseCFTypes`,
  latency 0), a directory kqueue source (`O_EVTONLY`, what a `DispatchSourceFileSystemObject`
  sees) and a 2 ms poller printing birth/mtime/ctime (ns), size and the xattr set, including
  hidden files.
- `spikeprefs.swift` - `CFPreferencesSetValue` + `CFPreferencesAppSynchronize` on
  `com.apple.screencapture` (`set`, `del`, `get`, and a long-lived `watch`).
- `spikedump.sh` - `stat -f "%FB %Fm %Fc %z"`, `xattr -l`, `mdls` per file.
- `spikecapture.sh` - display, selection and window capture for one `type`.
- `summarize.py`, `marker_latency.py` - condense the watcher log.
- `spikewindows.swift`, `spikeax.swift` - screencaptureui window probe, AX dump.
- `tccprobe.swift` + `build-tccprobe.sh` - throwaway ad-hoc signed app for the TCC probe.

Raw outputs: `ClipShotTests/Fixtures/spike/` (home folder replaced by `~`).

## Findings

### F1 - Marker and capture type: present on every format and mode that saves a file

`png jpg heic tiff pdf` x `display selection window`: every file that was produced carries
`com.apple.metadata:kMDItemIsScreenCapture` (= 1) and `kMDItemScreenCaptureType`
(`display` / `selection` / `window`), plus `kMDItemScreenCaptureGlobalRect`,
`com.apple.FinderInfo` and `com.apple.lastuseddate#PS`. 24 files, all with both xattrs
(`captures-metadata.txt`). Content types: `public.png`, `public.jpeg`, `public.heic`,
`public.tiff`, `com.adobe.pdf`. Two window captures (png first try, heic first try) produced no
file because the pointer was moved by the person at the Mac mid-gesture; both were retried and
saved (`placement-per-capture.txt`).

### F2 - PDF with the floating thumbnail on saves nothing

With `type=pdf` and `show-thumbnail=1`, display, selection and window captures produced no file
anywhere (4 attempts, no crash report; screencaptureui exits about 5.7 s after the capture).
With the thumbnail off, display and selection PDFs save normally; a PDF window capture saved
nothing in 2 attempts while a PNG window capture right after it worked. This is a macOS bug, not
a marker problem: nothing appears, so there is nothing to copy.

Evidence: `placement-per-capture.txt` (the `CAP ... pdf` events with `NO FILE`, and the
thumbnail-off ones that saved), `pdf-thumbnail-on-screencaptureui-lifetime.txt` (screencaptureui
pid and windows during the retry, transcribed from the console). "No crash report" was observed
in `~/Library/Logs/DiagnosticReports` and not recorded.

### F3 - Full-screen capture writes one file per display

`Cmd+Shift+3` on two displays writes `Screenshot <ts>.png` (main display) and then
`Screenshot <ts> (2).png` (second display) about 10 ms apart, each fully marked, each with its
own `kMDItemScreenCaptureGlobalRect`. A coordinator that copies every fresh marked file ends with
the **second display's image** on the clipboard.

### F4 - Write sequence

Thumbnail on (`seq-normal-thumbnail-on.txt`):

1. `.Screenshot <ts>.png` appears already at full size (one write; birth to mtime 0.1-0.8 ms for
   png/jpg/heic, up to 12 ms tiff, up to 105 ms pdf), no xattrs.
2. `com.apple.FinderInfo` set.
3. Renamed to `Screenshot <ts>.png`; `com.apple.lastuseddate#PS` set.
4. Marker xattrs (`kMDItemIsScreenCapture`, `kMDItemScreenCaptureType`, `...GlobalRect`) set
   **after** the final rename: 0-54 ms later, typically about 2 ms
   (`marker-latency.txt`, max 53.8 ms on a 33 MB TIFF, 30.5 ms on the Desktop fallback).

Thumbnail off (`seq-normal-thumbnail-off.txt`): `..Screenshot <ts>.png-XXXXXX` is created and
written incrementally (about 120 ms for 4 MB), renamed to `.Screenshot <ts>.png`, then to
`Screenshot <ts>.png`, then marked 2-4 ms later. mtime - birth up to 118 ms.

Temporary names always start with `.`; the final name never changes after the marker is set.

### F5 - What a watcher sees

- The directory kqueue source fires (`mask=2`, write) on the creates and renames, **not** when
  the marker xattrs are set. On the event for the final name the marker is usually not there yet,
  so the coordinator must rescan. A first rescan at 250 ms covers every observed case (max 54 ms).
- FSEvents with file events reports `Created|Renamed|Modified|FinderInfoMod|XattrMod|IsFile` on
  the temp name and `Renamed|XattrMod|IsFile` on the final name, but in this environment the
  events arrived in batches 0.2-300 s late (median 20.8 s over 35 deliveries,
  `fsevents-delay.txt`), even with latency 0 and `NoDefer`. The spike processes ran inside the
  agent's sandbox, so this delay is not proven for a normal app; do not depend on FSEvents for
  latency.

### F6 - Birth time is when the file is written, not when the capture was taken

Normal capture with the thumbnail on: file appears about 5-6 s after the shortcut; with the
thumbnail off about 150 ms. Thumbnail held by hover: capture at 16:57:00, birth 62.6 s later
(`seq-hover-hold-62s.txt`). In every case birth = the moment the file appears (within 1 ms of
the first directory event) and mtime = birth + at most 118 ms for screenshots. The name keeps the
capture time, so it must not be used for freshness.

### F7 - Markup Done writes once

Capture, click the thumbnail, Markup, two strokes, Done after 42.8 s: one file is written about
14 ms after Done, with the edits (verified visually), same sequence as F4, marked 3 ms after the
rename (`seq-markup-done-43s.txt`). The original is not written first. birth = Done.

### F8 - Hover holds the thumbnail

The thumbnail stays while the pointer rests on it (held 55 s); the file is written about 6 s
after the pointer leaves. A first attempt (hover started 0.7 s after the capture, while the
pointer was also being moved by the person at the Mac) did not hold it; cause not isolated.

### F9 - Screen recordings use a different marker

`Cmd+Shift+5` full-screen recording (`recording-metadata.txt`, `seq-screen-recording.txt`):
the `.mov` has `com.apple.metadata:kMDItemIsScreenRecording` (not `kMDItemIsScreenCapture`;
`mdls` shows `kMDItemIsScreenCapture = (null)`), `kMDItemScreenCaptureType = "display"` and a
GlobalRect. It appears by rename with birth = recording start (11.6 s before it appeared) and
mtime 5.6 s before it appeared. A filter that requires `kMDItemIsScreenCapture` excludes
recordings by itself; a filter on `kMDItemScreenCaptureType` alone would not. In
`marker-latency.txt` the `.mov` row measures the arrival of `kMDItemScreenCaptureType` only
(the script counts that for `.mov`); the `.mov` never gets an `isCap` marker.

### F10 - Applying prefs: screencaptureui caches them while it runs

- screencaptureui is started per capture and exits on its own about 5-6 s after the last file is
  saved (about 11-12 s after a thumbnail-on capture; with the Cmd+Shift+5 toolbar it lives until
  the toolbar closes).
- Writing `location*`, `show-thumbnail`, `target*` with `CFPreferencesSetValue` +
  `CFPreferencesAppSynchronize` and doing **nothing** else: the next capture honoured the change
  every time screencaptureui was not running (location r1, r2, r4; show-thumbnail off; target
  clipboard).
- While screencaptureui was running, a capture went to the **old** folder (B in
  `steps-timeline.log`).
- `killall SystemUIServer` with screencaptureui running: next capture still went to the old
  folder (Z). It is not the refresher.
- `killall screencaptureui` after its file was saved: next capture honoured the change (Y).
- `killall screencaptureui` while a thumbnail was pending: **that screenshot was lost**, no file
  anywhere (F).

Minimal reliable rule: write with CFPreferences; if screencaptureui is not running, nothing else
is needed; if it is running, wait for it to exit (it does so by itself) and never kill it.

### F11 - No host-scoped keys

`defaults -currentHost read com.apple.screencapture` -> `Domain 'com.apple.screencapture' not
found` (before and after the spike; `currenthost-read.txt` records the after run, the before run
was observed on the console). Everything lives in the any-host user domain.

### F12 - Cmd+Shift+5 Options writes tilde paths, visible at once to another process

Choosing Options > Save to > Documents (record mode active) wrote `location`,
`location-screenshot` and `location-screenrecording` all as `~/Documents/` (tilde, trailing
slash) plus `location-last`. A separate long-running process that calls
`CFPreferencesAppSynchronize` + `CFPreferencesCopyAppValue` every 500 ms saw the change at its
next poll, without any restart (`prefs-watch-cmd-shift-5-options.log`). The toolbar also writes
`last-selection` and `last-selection-display`. Options has a "Capture Format" submenu that was
not explored.

### F13 - target is honoured

`target`/`target-screenshot` = `clipboard` (screencaptureui not running): no file, the clipboard
held `PNGf` plus AVIF, PSD, GIF, JP2, JPEG, TIFF flavours. Set back to `file` afterwards.

### F14 - Missing folder falls back to the Desktop

`location*` pointing to a folder that was then moved to the Trash: the capture was saved to
`~/Desktop`; the prefs were left unchanged and the folder was not recreated. The Desktop file
also had `com.apple.macl` and was marked 30 ms after appearing
(`seq-missing-folder-fallback.txt`, `missing-folder-fallback.txt`).

### F15 - TCC: the first Desktop access blocks the calling thread

Ad-hoc signed `TCCProbe.app` (bundle id `sk.moravcik.clipshot.tccprobe`, with
`NSDesktopFolderUsageDescription`) launched through LaunchServices so it is its own responsible
process (`tcc-probe-first-launch.log`):

- `open(~/Desktop, O_EVTONLY)` on a background thread **blocked 7.9 s**, then returned a valid
  fd; `contentsOfDirectory` then took 2 ms and returned the items. The block is the consent
  prompt waiting for an answer (someone at the Mac answered it; the prompt itself was not
  captured).
- Second launch: 15 ms, no block (`tcc-probe-second-launch.log`).
- The same probe source run from the terminal (already granted): 0 ms (`tcc-probe-terminal.txt`,
  re-run after the spike).
- Not verified: the "Don't Allow" path (error vs. empty listing).
- `x-apple.systempreferences:com.apple.preference.security?Privacy_FilesAndFolders` opens
  System Settings on the "Files & Folders" pane (window title read via AX;
  `tcc-settings-deeplink.txt`, transcribed from the console).

### F16 - `defaults import` merges

Restoring the backup with `defaults import` left the spike's extra keys (`type`,
`location-last`, `last-selection`, `last-selection-display`) in place; they had to be deleted.
A restore must delete the keys that were absent from the backup (`defaults-import-merge.txt`:
backup keys, the post-import diff transcribed from the console, the deletes, and the final
empty diff).

### F17 - A renamed screenshot keeps its marker and birth time

`mv` within the volume kept birth, mtime and all marker xattrs (last row of
`marker-latency.txt`). The marker cannot tell a renamed screenshot from an untouched one; only
the ledger path can.

### F-markup - Native Markup from a third-party app (Task 12b, 2026-10-20)

Probed on macOS 27.0.1 with an ad-hoc, non-sandboxed probe on a 400x300 PNG carrying the
marker xattrs, with the session locked (no clicks possible). Probes:
`scripts/spike/markup_ql.swift`, `scripts/spike/markup_share.swift`. 30-minute cap.

1. **Quick Look panel with Markup.** `QLPreviewPanel` has no public editing API on macOS
   (the SDK headers have none). The panel does ask its delegate two undocumented informal
   selectors, `previewPanel:canEditItem:` and `previewPanel:saveModeForItem:` (also present:
   `previewPanel:didUpdateContentsOfPreviewItem:`,
   `previewPanel:didSaveEditedCopyOfPreviewItem:atURL:`). With `canEditItem` = YES and save
   mode 1 the controller still reported `markupEnabled = 0`, and `markupFromButton:` did not
   enter Markup. Not usable: private API, and it did not work in the probe.
2. **System Markup extension.** `com.apple.MarkupUI.Markup` (an `com.apple.ui-services`
   editor extension in `MarkupUI.framework/PlugIns/Markup.appex`) is reachable through the
   public `NSSharingService(named:)` with the extension's identifier. `canPerform` is true for
   a PNG file URL. `perform(withItems:)` asked the delegate for a source window and presented
   the editor over it (`SHKRemoteWindow`, `SHKDimAndShadowWindow`, `SHKBlurWindow`, and a
   `Markup` extension process). **Usable.** Not verified: what Done returns. The extension's
   strings show it calls `completeRequestReturningItems:` and `writeToURL:error:`, so the edit
   is either written to the shared file in place or returned to the host; Done needs a click,
   which a locked session cannot give.
3. **Preview.app.** Always available; the user picks Markup there and Preview saves in place.

**Decision:** ClipShot uses the Markup extension (2) and falls back to Preview.app (3) when the
service is missing, cannot perform, or fails. While the editor is open the file is in an edit
session: a write to it copies even when the file is older than 30 s, and an edited copy that
loses the screenshot marker still copies. When Done returns an edited copy instead of writing
in place, ClipShot copies that image to the clipboard and leaves the original file as it is
(ClipShot never writes over a user's file); the log records which of the two happened
(`markup done in place` / `markup done as copy`), so the first real edit on the installed
build settles it.

Not verified: in-place write, its inode and birth time, and which xattrs survive the edit.
The probe ran on macOS 27.0.1; ClipShot's minimum is macOS 26, where
`com.apple.MarkupUI.Markup` is unverified. Where `NSSharingService(named:)` returns nil or
cannot perform, ClipShot opens the file in Preview.app instead (covered by
`MarkupOpenerTests.missingExtensionFallsBackToPreview`). F7
(the macOS thumbnail's own Markup) writes a new file by rename with a fresh marker; the edit
session matches the file by its path or its inode, never by the marker.

## Contradictions with the spec and new rules for later tasks

1. **Refresher (spec: "we needed `killall SystemUIServer` on 27.0.1")** - wrong for 27.0.1.
   `killall SystemUIServer` does not make a running screencaptureui pick up new prefs, and
   `killall screencaptureui` can destroy a pending screenshot (F10). Rule: CFPreferences write,
   then wait until screencaptureui is not running; never kill either process.
2. **Location values can be tilde paths** (`~/Documents/`, F12). Expand the tilde and
   standardise before comparing or watching.
3. **Two displays, one shortcut, two files** (F3). Copying every fresh marked file puts the
   second display on the clipboard. Needs a decision (for example, copy only the file whose
   GlobalRect contains the main display, or the first of a group written within 100 ms).
4. **Restore previous settings** must delete keys absent from the backup, not only write the
   backed-up values (F16).
5. **Temp names** start with `.` (and `..` with a random suffix when the thumbnail is off); the
   watcher must ignore dot-files and never act on the first directory event alone (F4, F5).
6. Spec statement "real captures have birth and mtime within about 1 ms" holds with the thumbnail
   on for png/jpg/heic; with the thumbnail off, or for tiff/pdf, the gap reaches 118 ms. The 30 s
   freshness rule is unaffected.
7. `.mov` exclusion is automatic when retention requires `kMDItemIsScreenCapture` (F9); keep
   the explicit extension filter as the spec asks.

## Reproduce

Needs Accessibility for the terminal (for `spikeinput`) and a second terminal tab. `B` is any
scratch folder for the binaries; `S` is a throwaway capture folder.

```sh
B=/tmp/spike-bin; S=~/Pictures/Screenshots/clipshot-spike; mkdir -p $B $S/{r1,r2,r3,r4,caps,flow,rec,gone}
for t in spikewatch spikeprefs spikeinput spikewindows spikeax; do swiftc -O scripts/spike/$t.swift -o $B/$t; done
defaults export com.apple.screencapture $B/screencapture-before.plist        # backup first

# tab 2: watcher (FSEvents + kqueue + 2 ms poller), Ctrl-C to stop
$B/spikewatch ~/Pictures/Screenshots $S/{r1,r2,r3,r4,caps,flow,rec,gone} ~/Desktop ~/Documents > $B/watch.log

# point the folder (no refresher), wait until screencaptureui is gone, capture
for k in location location-screenshot location-screenrecording; do $B/spikeprefs set $k $S/caps; done
while pgrep -q screencaptureui; do sleep 0.25; done
scripts/spike/spikecapture.sh png $B $B/steps.log      # display, selection, window; repeat for jpg heic tiff pdf

# refresher tests (F10): change prefs while screencaptureui runs, then capture
$B/spikeinput key 20 cmd,shift                         # Cmd+Shift+3
$B/spikeprefs set location $S/r2; killall screencaptureui   # or killall SystemUIServer, or nothing

# analysis
scripts/spike/spikedump.sh $S/caps/*                   # stat, xattr -l, mdls per file
scripts/spike/summarize.py $B/watch.log <from_ns> <to_ns> [--grep caps/]
scripts/spike/marker_latency.py $B/watch.log
scripts/spike/fsevents_delay.py $B/watch.log
scripts/spike/placement.py $B/steps.log --watch $B/watch.log --final <listing>

# Options visibility (F12): leave running, change Save to in Cmd+Shift+5 Options
$B/spikeprefs watch 300

# TCC probe (F15)
scripts/spike/build-tccprobe.sh $B && open -n $B/TCCProbe.app --args $B/probe.log

# restore: import merges (F16), so also delete keys that were not in the backup
defaults import com.apple.screencapture $B/screencapture-before.plist
diff <(plutil -p $B/screencapture-before.plist) <(defaults export com.apple.screencapture - | plutil -p -)
```

Key codes for `spikeinput key`: 20 = 3, 21 = 4, 23 = 5, 49 = Space, 53 = Escape. Points are
global, top-left origin. The thumbnail of a 400x300 pt selection on the 1800x1169 pt main display
sat at about (1600-1788, 1031-1156); find it with `screencapture -x -R...` while it shows.

## Not verified

- FSEvents latency for a normal (non-sandboxed) app (F5).
- TCC "Don't Allow" behaviour (F15).
- The "Capture Format" submenu in Cmd+Shift+5 Options and which key it writes.
- A pref change with screencaptureui running was tested for `location` only; `show-thumbnail`
  and `target` were tested only with screencaptureui not running.
